CAN ID 15｜控制

SysId 系統鑑別：體適能檢測

第 13 章的參數是用「試」的，這章要改成用「量」的。我們會講 SysId 在量什麼、四項測試在做什麼、資料怎麼變成 kS、kV、kA、kG，還有怎麼判斷資料能不能信。後半段是實作：在手臂上用 SysIdRoutine 配 Phoenix 的 SignalLogger 收資料、把 hoot 檔轉成 SysId 看得懂的格式，最後把結果填回程式。

版本說明這章是照 WPILib 2026 和 Phoenix 6 的 2026 版（26.x）文件寫的。SysId 不用另外裝，WPILib 安裝程式就附了。

先講個比喻：體適能檢測

體育老師要幫每個同學排訓練課表，可以憑感覺猜「他大概跑多快」，但更好的方法是做體適能檢測，讓數據說話。第 13 章的手動調參就是憑感覺猜，這章要做的是檢測。

檢測有兩種項目。第一種是「漸速跑」：跑步機的速度一點一點慢慢調高，同學幾乎沒有在「加速」，所以量到的主要是「維持某個速度要花多少力」。第二種是「起跑衝刺」：槍一響就全力衝，量的是「身體要加速有多吃力」。

兩種都要往前做一次、往回做一次，總共四項。往前做完馬上做往回，剛好也回到起點。

檢測時老師一定要在旁邊看著，因為跑步機不會自己停，快撞牆了要有人喊停。檢測只負責出題，安全要自己顧。

最後成績交給電腦，電腦用一套公式去配合數據，算出這個同學的各項數值。算出來的數字是很好的起點，但不保證完美，真的上課還是要再微調。

比喻SysId
憑感覺猜 vs. 做檢測手動調參 vs. 系統鑑別

這個比喻哪裡不準同學會累，每天測出來都不一樣；馬達不會累，但會變熱，電池電壓也會掉。所以測試要用電充飽的電池，每項也不要測太久。還有，SysId 用的是固定的物理模型（第 13 章的電壓平衡方程式），機構如果有模型沒描述到的東西，像很大的背隙或會卡住的地方，結果就會不準。

SysId 在量什麼

系統鑑別就是分析輸入和輸出的資料，找出一個能描述系統行為的數學模型。SysId 用最小平方法這類曲線擬合，從實際量測裡把模型的係數找出來[1]。它支援三種模型[1]：

分析類型模型適合
Simple MotorV = kS·sgn(v) + kV·v + kA·a飛輪、轉塔、水平滑軌
ElevatorV = kG + kS·sgn(v) + kV·v + kA·a升降機構
ArmV = kG·cos(θ) + kS·sgn(ω) + kV·ω + kA·α手臂

有沒有很眼熟？這三條就是第 13 章的前饋方程式。SysId 做的事，就是幫你的機構把式子裡的係數找出來。

四項測試

標準流程有兩種測試[2]：

  • Quasistatic：讓機構非常慢地加速，所以跟加速度有關的電壓可以忽略（「近乎靜態」的意思）。
  • Dynamic：直接給機構一個固定的「步階電壓」，量它加速時的表現。

兩種都要往前、往後各做一次，共四項。順序隨意，但建議往前做完馬上做往後，機構大概會回到原位[2]。

收了哪些資料

每個取樣點會記三樣東西：馬達的電壓、機構的位置和速度，再加上現在在跑哪一項測試（SysId 用「state」字串來分段）[7]。加速度沒有直接量，是從速度變化算出來的，所以雜訊特別多。

每一個點都代進同一條式子。拿升降機構當例子：

V = kS·sgn(v) + kG + kV·v + kA·a

一次測試有幾百個點，就有幾百條這種式子，但未知數只有 kS、kG、kV、kA 四個。每個點都有量測誤差，不可能每一條都剛好成立。

回歸：從資料找出係數

所以 SysId 用最小平方法這類曲線擬合：找一組 kS、kG、kV、kA，讓所有點的「預測電壓」跟「實際電壓」的差距平方加起來最小[1]。四項測試各自負責讓某幾個係數分得出來：

測試資料的特性主要幫忙分辨
Quasistatic加速度幾乎是 0，電壓和速度幾乎是一條直線斜率 ≈ kV；截距裡有 kS 與 kG
Dynamic突然給固定電壓，加速度很大kA
正向＋反向摩擦方向相反，重力方向不變把 kS 和 kG 分開

最後一列就是「為什麼一定要做正反兩個方向」。升降機構往上時截距是 kG + kS，往下時是 kG − kS（摩擦反過來，重力不變）。只做一個方向，你就只看得到兩個加起來，分不開。手臂的 kG 還要乘 cos θ、會隨角度變，所以分得開，但判斷摩擦一樣要兩個方向。

怎麼判斷資料能不能信

SysId 的 Diagnostics 區塊有三個擬合指標[9]：

  • 模擬速度 r²：拿擬合出來的參數，從實際電壓模擬出速度，再跟量到的速度比。大於 0.9 就是擬合得不錯。
  • 加速度 r²：機構會振動，加速度很吵，就算很好的資料也很少超過 0.5；低於大概 0.2 的話，kA 就很可疑了。
  • 模擬速度 RMSE：模擬速度誤差的標準差，可以當成這次測試雜訊有多大的估計。

數字之外也要看圖。好的 quasistatic 速度對時間圖幾乎是一條直線，dynamic 則是像指數那樣慢慢靠近穩定速度。長得不像，就代表機構設定、分析設定或測試過程有問題。常見的壞資料有這些[9]：

狀況圖上看起來怎麼處理
速度門檻太低quasistatic 圖前面有一段「尾巴」：還沒開始動的點被算進去調高 Velocity Threshold 重新分析
速度門檻太高加速度對速度的圖中間有一大段空白調低門檻重新分析
速度訊號雜訊大圖上的點上下亂跳檢查編碼器安裝（軸心、磁鐵位置）；可以加大 Window Size，但根本原因還是要修
撞到機械極限速度突然掉到 0，電壓卻還在升丟掉那段資料，下次提早放開

另外，機構比馬達輕很多的時候，kA 會趨近 0，前饋可以不管它；但 kA 量不準的話，算出來的回饋增益也會不準，要手動調[9]。

為什麼和理論值不一樣

第 13 章的 kG、kV、kA 可以用質量、齒輪比和馬達常數去估 [MODEL]，但 SysId [SYSID] 量到的幾乎一定不一樣。常見的原因是：

  • 模型沒算到的東西：齒輪箱和鏈條的效率損失、軸承摩擦、線材的拉力、螺絲和電線的質量。
  • 模型的假設本來就有誤差：質量、力臂或重心估錯；每顆馬達的常數也都有一點個體差異。
  • 機構資料填錯：差很多（差好幾倍那種）的時候，通常不是摩擦，而是齒輪比、鼓輪半徑或單位填錯了。工具站 4F 單元二會拿 SysId 結果跟理論值比，幫你推測可能填錯哪個（看本章的工具站任務）。

差一點是正常的，這也是為什麼要量：理論值告訴你數量級對不對，SysId 告訴你真實的機構到底是多少。

寫 SysIdRoutine

WPILib 有一個 SysIdRoutine：Config 寫測試設定（quasistatic 的電壓上升速率、dynamic 的步階電壓、安全用的最長時間、記錄測試狀態的回呼），Mechanism 寫怎麼驅動馬達、怎麼記錄資料[2]。routine 和回呼建議都寫在 Subsystem 裡[2]。

用 TalonFX 的話，建議不要讓 SysIdRoutine 自己記錄，改用 Phoenix 的 SignalLogger[2]。它會自動抓所有狀態訊號，帶著 CAN 上的時間戳，而且不受主迴圈時間和 Java GC 影響，系統鑑別會準很多[3]。下面照 CTRE 官方 SysId 範例的寫法[4]，加進第 6 章的 ArmSubsystem：

import static edu.wpi.first.units.Units.*;

import com.ctre.phoenix6.SignalLogger;
import edu.wpi.first.wpilibj2.command.sysid.SysIdRoutine;

public class ArmSubsystem extends SubsystemBase {
    // ...第 6 章的欄位

    private final SysIdRoutine sysId = new SysIdRoutine(
        new SysIdRoutine.Config(
            Volts.of(0.5).per(Second), // TODO: quasistatic 上升速率，手臂行程短，比預設 1 V/s 慢
            Volts.of(2.0),             // TODO: dynamic 步階電壓，比預設小，避免手臂甩太快
            Seconds.of(5.0),           // TODO: 最長時間
            state -> SignalLogger.writeString("state", state.toString())),
        new SysIdRoutine.Mechanism(
            volts -> { mode = ControlMode.VOLTAGE; manualVolts = volts.in(Volts); },
            null, // 由 SignalLogger 記錄，不用 WPILib 的記錄
            this));

    public Command sysIdQuasistatic(SysIdRoutine.Direction direction) {
        return sysId.quasistatic(direction);
    }

    public Command sysIdDynamic(SysIdRoutine.Direction direction) {
        return sysId.dynamic(direction);
    }
}

幾個重點：

  • 電壓回呼沒有直接呼叫 IO，而是切到第 6 章的 ControlMode.VOLTAGE，讓 periodic 去送電壓。不然下一輪的 setPositionGoal 會把它蓋掉。
  • 測試指令結束後 mode 還停在 VOLTAGE，手臂不會自己回到位置控制，要等下一次呼叫 setGoal 才會切回去。測完記得先讓手臂回到安全位置。
  • CTRE 範例把 dynamic 電壓降到 4 V，避免電壓驟降（brownout）[4]。手臂行程很短，這裡示範更小的值；實際數字要看機構調。
  • CTRE 範例也把會用到的 Position、Velocity、MotorVoltage 訊號拉到 250 Hz，資料比較密[4]。

在 RobotContainer 把四項測試綁到按鍵上，按住才跑、放開馬上停（第 9 章的 whileTrue）。CTRE 範例也是用兩個按鍵手動開始、停止記錄[4]：

// 只在測試用的配置裡綁定，比賽用的配置不要有
controller.leftBumper().onTrue(Commands.runOnce(SignalLogger::start));
controller.rightBumper().onTrue(Commands.runOnce(SignalLogger::stop));

controller.y().whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kForward));
controller.a().whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kReverse));
controller.b().whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kForward));
controller.x().whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kReverse));

跑測試

  1. 換一顆充飽的電池，確認機構旁邊沒人。
  2. 手臂放在行程中間，Enable（Teleop）。
  3. 按開始記錄。
  4. 按住 Y（quasistatic 往前），手臂快到上限前放開；接著按住 A（往後），快到下限前放開。
  5. B、X（dynamic）也一樣。dynamic 動得很快，要更早放。
  6. 按停止記錄，然後 Disable。
SysIdRoutine 不會幫你停routine 只會一直送電壓命令，快超出安全範圍時要你自己提早放開，軟硬體極限也要自己設好[5]。第 6 章的軟體極限（SoftwareLimitSwitch）測試時一定要開著。
一份日誌只能有一個 routine只有「裡面只有一個 routine」的日誌才能拿去分析。多顆馬達可以放在同一個 routine 裡一起跑，但如果你先測一個機構、再測另一個，中間沒有取出日誌或重開 roboRIO，分析就會失敗[5]。用 SignalLogger 的話，每測完一個機構就 stop，再 start 開新檔。

補充一下：在 roboRIO 2（或插著 USB 隨身碟的 roboRIO 1）上，SignalLogger 預設會在開機後、機器人被 Enable 或 Driver Station 連上時自動開始記錄[3]。手動 start / stop 可以讓一個檔案裡只有這次的測試，比較好找。

取出資料並分析

  1. 拿出 hoot 檔。用 Tuner X 左邊的檔案總管下載 hoot 日誌，下載完會自動丟進右邊的轉檔佇列[6]。
  2. 轉成 WPILog。在 Convert 分頁選 wpilog 格式轉檔。可以用篩選只留要的訊號，例如某顆 TalonFX 的 MotorVoltage、Position、Velocity[6]。沒有 Pro 的裝置只能匯出一部分免費訊號，還好 TalonFX 的 Position、Velocity、MotorVoltage 都在免費清單裡[3]。
  3. 載入 SysId。在 Log Loader 開檔，把名稱有 "state" 的字串項目拖到 Test State，再把 Position、Velocity、Voltage 拖到對應的欄位[7]。
  4. 檢查單位和分析類型。手臂選 Arm。單位不對的話用 Data Selector 的 Units 修正[7]。有設 SensorToMechanismRatio 的 TalonFX，Position、Velocity 已經是手臂端的 rotations、rot/s 了。
  5. 看 Feedforward 結果。畫面上會顯示算出來的 kS、kV、kA、kG。

Feedback 區塊也會用 LQR 算出建議的 kP、kD，不過 WPILib 自己都說這只是「有根據的猜測」，不保證完美，當成往下調的起點就好[8]。要讓建議值對得上 TalonFX 的控制器，Gain Settings Preset 和 Controller Type 要選對[8]。

把結果填回程式

SysId 的單位要跟 Phoenix 6 Slot0 的單位一樣：載入的資料如果是手臂端 rotations，得到的 kV 就是 V/(rot/s)、kA 是 V/(rot/s²)，可以直接填進 Slot0。

// 量測日期：YYYY-MM-DD，電池編號：__，SysId 資料檔：__
config.Slot0.GravityType = GravityTypeValue.Arm_Cosine;
config.Slot0.kS = 0.0; // [SYSID] TODO: SysId
config.Slot0.kG = 0.0; // [SYSID] TODO: SysId
config.Slot0.kV = 0.0; // [SYSID] TODO: SysId，V/(rot/s)
config.Slot0.kA = 0.0; // [SYSID] TODO: SysId，V/(rot/s²)
config.Slot0.kP = 0.0; // [TUNED] TODO: 從 SysId 建議值開始，再上機微調
config.Slot0.kD = 0.0; // [TUNED] TODO

// 用 MotionMagic Expo 時（第 14 章），也可以用 kV、kA 當起點
config.MotionMagic.MotionMagicExpo_kV = 0.0; // [SYSID] TODO
config.MotionMagic.MotionMagicExpo_kA = 0.0; // [SYSID] TODO

量測日期、用哪顆電池、資料檔名都寫在註解裡。機構只要改過（換馬達、改齒輪比、加重量）就要重測。

順帶一提，SysId 算出來的前饋不只能用在軌跡追蹤，連開迴路控制都會變好操作，因為搖桿推多少，機構的反應會更接近你預期的[1]。

常見錯誤

手臂的 0 度不是水平Arm 模型用 cos(θ)，θ 是跟水平的夾角。0 度不是水平的話算出來的 kG 會錯，手臂在某些角度會撐不住（第 12 章的 MagnetOffset）。
一個日誌裡混了好幾次測試先測手臂再測升降，卻沒有分開記錄，SysId 會分析失敗，或給你很怪的結果。
測試時撞到極限撞到機械極限那段資料會讓擬合跑掉，還可能把機構撞壞。每項測試都要在快到極限前放開。
拿快沒電的電池測dynamic 測試時電壓驟降，資料變很爛，嚴重的話 roboRIO 直接 brownout。
把 SysId 的 kP 當最終答案回饋增益只是起點，還是要上機確認不會晃、不會抖。

小測驗

練習：測試用的按鍵配置

比賽時絕對不能誤觸到 SysId。改寫上面的綁定，讓四個按鍵只有在 Test 模式（第 7 章）時才會跑 SysId。

兩個條件都成立才執行，第 9 章教過怎麼組合 Trigger。

用 new Trigger(DriverStation::isTest) 表示「在 Test 模式」，再用 .and(...) 和按鍵組合。

controller.y().and(testMode).whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kForward)); 其他三個照同樣寫法。

Trigger testMode = new Trigger(DriverStation::isTest);

controller.y().and(testMode).whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kForward));
controller.a().and(testMode).whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kReverse));
controller.b().and(testMode).whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kForward));
controller.x().and(testMode).whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kReverse));

用第 9 章的 and 組合條件，兩個都成立 Trigger 才會是 true。放開按鍵或離開 Test 模式，whileTrue 就會取消指令。第 7 章的 Robot.java 把 CommandScheduler.getInstance().run() 放在 robotPeriodic()，所以 Test 模式下排程器照樣在跑；testInit() 的 cancelAll() 則確保一進 Test 就先把其他指令停掉。
