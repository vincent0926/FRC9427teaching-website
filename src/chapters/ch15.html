CAN ID 15｜控制

SysId 系統鑑別：體適能檢測

讀完這章，你會知道 SysId 在量什麼、四項測試是什麼、怎麼在手臂上用 SysIdRoutine 搭配 Phoenix 的 SignalLogger 收資料、怎麼把 hoot 檔轉成 SysId 讀得懂的格式，以及怎麼把算出來的 kS、kV、kA、kG 填回程式。

版本說明本章依據 WPILib 2026 與 Phoenix 6 的 2026 版（26.x）文件。SysId 隨 WPILib 安裝程式一起安裝。

生活比喻：體適能檢測

體育老師不猜，而是量。要幫每位同學排訓練課表，老師可以憑感覺猜「他大概跑多快」，但更好的做法是做體適能檢測，用數據說話。第 13 章的手動調參就像憑感覺猜，這一章要做的是檢測。

檢測有兩種項目。第一種是「漸速跑」：跑步機的速度一點一點慢慢調高，這時候同學幾乎沒有在「加速」，量到的主要是「維持某個速度要花多少力」。第二種是「起跑衝刺」：槍聲一響就全力起跑，量到的是「身體要加速有多吃力」。

往前、往回各做一次。兩種項目都要往前做一次、往回做一次，總共四項。做完往前立刻做往回，剛好也回到起點。

檢測時老師要在旁邊看著。跑步機不會自己停，跑到快撞牆了，老師要喊停。檢測本身只負責出題，安全要自己顧。

成績單交給分析軟體。檢測記錄交給電腦，電腦用一套公式去配合數據，算出這位同學的各項數值。算出來的數字是很好的起點，但不是保證完美，實際上課還要再微調。

這個比喻哪裡不準同學會累，檢測結果每天不同；馬達不會累，但會變熱，電池電壓也會下降。所以測試要用電量充足的電池，而且每項測試時間不長。另外，SysId 用的公式是固定的物理模型（第 13 章的電壓平衡方程式），機構如果有模型沒描述到的東西，例如很大的背隙或會卡住的地方，結果就會不準。

SysId 在量什麼

WPILib 文件說明，系統鑑別是透過分析輸入與輸出的統計資料，找出描述系統行為的數學模型；SysId 會用最小平方法等曲線擬合技術，從實際量測中找出模型係數[1]。它支援三種模型[1]：

分析類型模型適合
Simple MotorV = kS·sgn(v) + kV·v + kA·a飛輪、轉塔、水平滑軌
ElevatorV = kG + kS·sgn(v) + kV·v + kA·a升降機構
ArmV = kG·cos(θ) + kS·sgn(ω) + kV·ω + kA·α手臂

這三個式子就是第 13 章的前饋方程式。SysId 做的事，就是替你的機構找出式子裡的係數。

四項測試

WPILib 文件說明，標準的鑑別流程有兩種測試[2]：

  • Quasistatic：機構被非常緩慢地加速，所以和加速度有關的電壓可以忽略（「近乎靜態」）。
  • Dynamic：給機構一個固定的「步階電壓」，用來量加速時的行為。

兩種測試都要往前、往後各做一次，共四項。順序不拘，但建議做完往前立刻做往後，機構大致會回到原位[2]。

寫 SysIdRoutine

WPILib 提供 SysIdRoutine：Config 描述測試設定（quasistatic 的電壓上升速率、dynamic 的步階電壓、安全用的最長時間、記錄測試狀態的回呼），Mechanism 描述怎麼驅動馬達和記錄資料[2]。文件建議把 routine 和回呼都寫在 Subsystem 裡[2]。

用 TalonFX 時，CTRE 建議不用 SysIdRoutine 自己記錄，而是用 Phoenix 的 SignalLogger[2]。它的好處是自動擷取所有狀態訊號、帶著 CAN 上的時間戳，而且不受主迴圈時間和 Java GC 影響，能明顯提高系統鑑別的準確度[3]。下面依照 CTRE 官方 SysId 範例的寫法[4]，加到第 6 章的 ArmSubsystem：

import static edu.wpi.first.units.Units.*;

import com.ctre.phoenix6.SignalLogger;
import edu.wpi.first.wpilibj2.command.sysid.SysIdRoutine;

public class ArmSubsystem extends SubsystemBase {
    // ...第 6 章的欄位

    private final SysIdRoutine sysId = new SysIdRoutine(
        new SysIdRoutine.Config(
            Volts.of(0.5).per(Second), // TODO: quasistatic 上升速率，手臂行程短，比預設 1 V/s 慢
            Volts.of(2.0),             // TODO: dynamic 步階電壓，比預設小，避免手臂甩太快
            Seconds.of(5.0),           // TODO: 最長時間
            state -> SignalLogger.writeString("state", state.toString())),
        new SysIdRoutine.Mechanism(
            volts -> { mode = ControlMode.VOLTAGE; manualVolts = volts.in(Volts); },
            null, // 由 SignalLogger 記錄，不用 WPILib 的記錄
            this));

    public Command sysIdQuasistatic(SysIdRoutine.Direction direction) {
        return sysId.quasistatic(direction);
    }

    public Command sysIdDynamic(SysIdRoutine.Direction direction) {
        return sysId.dynamic(direction);
    }
}

重點：

  • 電壓回呼沒有直接呼叫 IO，而是切換成第 6 章的 ControlMode.VOLTAGE，讓 periodic 送出電壓。這樣才不會被下一輪的 setPositionGoal 蓋掉。
  • 測試指令結束後，mode 仍然是 VOLTAGE，手臂不會自己回到位置控制；下一次呼叫 setGoal 才會切回。測完記得先讓手臂回到安全位置。
  • CTRE 範例把 dynamic 電壓降到 4 V 以避免電壓驟降（brownout）[4]。手臂行程很短，這裡示範更小的值；數值要依機構調整。
  • CTRE 範例也把要用到的 Position、Velocity、MotorVoltage 訊號提高到 250 Hz，讓資料更密[4]。

在 RobotContainer 裡把四項測試綁到按鍵上，按住才執行，放開立刻停止（第 9 章的 whileTrue）。CTRE 範例也用兩個按鍵手動開始、停止記錄[4]：

// 只在測試用的配置裡綁定，比賽用的配置不要有
controller.leftBumper().onTrue(Commands.runOnce(SignalLogger::start));
controller.rightBumper().onTrue(Commands.runOnce(SignalLogger::stop));

controller.y().whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kForward));
controller.a().whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kReverse));
controller.b().whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kForward));
controller.x().whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kReverse));

跑測試

  1. 換上充飽的電池，確認機構周圍沒有人。
  2. 把手臂放在行程中間，Enable（Teleop）。
  3. 按開始記錄。
  4. 按住 Y（quasistatic 往前），手臂接近上限前放開；接著按住 A（往後），接近下限前放開。
  5. 同樣做 B、X（dynamic）。dynamic 動得很快，要更早放開。
  6. 按停止記錄，再 Disable。
SysIdRoutine 不會替你停WPILib 文件警告：routine 只會產生電壓命令，超過安全範圍時要自己提早停止，軟硬體極限也要自己設好[5]。第 6 章的軟體極限（SoftwareLimitSwitch）在測試時一定要開著。
一份日誌只能有一個 routineWPILib 文件警告：只有「裡面只有一個 routine」的日誌檔能拿來分析。多顆馬達可以放在同一個 routine 裡同時跑，但如果先測一個機構、再測另一個，中間沒有取出日誌或重開 roboRIO，分析會失敗[5]。用 SignalLogger 時，每次測完一個機構就 stop，再 start 開新檔。

補充：CTRE 文件說明，在 roboRIO 2（或插著 USB 隨身碟的 roboRIO 1）上，SignalLogger 預設會在開機後、機器人被 Enable 或 Driver Station 連上時自動開始記錄[3]。手動 start / stop 可以讓一個檔案裡只有這次的測試，比較好找。

取出資料並分析

  1. 取出 hoot 檔。用 Tuner X 左側的檔案總管下載 hoot 日誌，下載後會自動放進右邊的轉檔佇列[6]。
  2. 轉成 WPILog。在 Convert 分頁選 wpilog 格式轉檔。可以用篩選只留下要的訊號，例如某顆 TalonFX 的 MotorVoltage、Position、Velocity[6]。沒有 Pro 授權的裝置只能匯出一部分免費訊號，但 TalonFX 的 Position、Velocity、MotorVoltage 都在免費清單裡[3]。
  3. 載入 SysId。在 Log Loader 開啟檔案，把名稱含 "state" 的字串項目拖到 Test State；再把 Position、Velocity、Voltage 拖到對應欄位[7]。
  4. 檢查單位與分析類型。手臂選 Arm。資料單位如果不對，用 Data Selector 的 Units 修正[7]。設了 SensorToMechanismRatio 的 TalonFX，Position、Velocity 已經是手臂端的 rotations、rot/s。
  5. 看 Feedforward 結果。畫面會顯示算出的 kS、kV、kA、kG。

Feedback 區塊也會用 LQR 算出建議的 kP、kD，但 WPILib 文件強調這些只是「有根據的猜測」，不保證完美，應該當成進一步調整的起點[8]。要讓建議值符合 TalonFX 的控制器，需要選對 Gain Settings Preset 與 Controller Type[8]。

把結果填回程式

SysId 的單位和 Phoenix 6 Slot0 的單位要一致：如果載入的資料是手臂端 rotations，得到的 kV 就是 V/(rot/s)、kA 是 V/(rot/s²)，可以直接填進 Slot0。

// 量測日期：YYYY-MM-DD，電池編號：__，SysId 資料檔：__
config.Slot0.GravityType = GravityTypeValue.Arm_Cosine;
config.Slot0.kS = 0.0; // TODO: SysId
config.Slot0.kG = 0.0; // TODO: SysId
config.Slot0.kV = 0.0; // TODO: SysId，V/(rot/s)
config.Slot0.kA = 0.0; // TODO: SysId，V/(rot/s²)
config.Slot0.kP = 0.0; // TODO: 從 SysId 建議值開始，再上機微調
config.Slot0.kD = 0.0; // TODO

// 用 MotionMagic Expo 時（第 14 章），也可以用 kV、kA 當起點
config.MotionMagic.MotionMagicExpo_kV = 0.0; // TODO
config.MotionMagic.MotionMagicExpo_kA = 0.0; // TODO

把量測日期、電池和資料檔寫在註解裡。機構改過（換馬達、改齒輪比、加重量）就要重測。

另外，WPILib 文件提到，SysId 算出的前饋不只能用在軌跡追蹤，也能讓開迴路控制更好操作，因為搖桿輸入會更接近機構的實際反應[1]。

常見錯誤

手臂的 0 度不是水平Arm 模型用 cos(θ)，θ 是和水平的夾角。0 度不是水平時算出的 kG 會錯，手臂在某些角度撐不住（第 12 章的 MagnetOffset）。
一個日誌裡混了好幾次測試先測手臂、再測升降，沒有分開記錄，SysId 會分析失敗或給出奇怪的結果。
測試時撞到極限撞到機械極限的那段資料會讓擬合失準，還可能損壞機構。每項測試都在接近極限前放開。
拿低電量電池測dynamic 測試時電壓驟降，資料品質變差，嚴重時 roboRIO brownout。
把 SysId 的 kP 當最終答案回饋增益只是起點，還是要上機確認沒有振盪或抖動。

小測驗

練習：測試用的按鍵配置

比賽時不應該能誤觸 SysId。請改寫上面的綁定：只有在 Test 模式（第 7 章）時，四個按鍵才會執行 SysId 測試。

要讓兩個條件都成立時才執行，第 9 章學過怎麼組合 Trigger。

用 new Trigger(DriverStation::isTest) 表示「在 Test 模式」，再用 .and(...) 和按鍵組合。

controller.y().and(testMode).whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kForward)); 其他三個照同樣寫法。

Trigger testMode = new Trigger(DriverStation::isTest);

controller.y().and(testMode).whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kForward));
controller.a().and(testMode).whileTrue(arm.sysIdQuasistatic(SysIdRoutine.Direction.kReverse));
controller.b().and(testMode).whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kForward));
controller.x().and(testMode).whileTrue(arm.sysIdDynamic(SysIdRoutine.Direction.kReverse));

用第 9 章的 and 組合條件：兩個條件都成立時 Trigger 才為真。按鍵放開或離開 Test 模式時，whileTrue 會取消指令。第 7 章的 Robot.java 把 CommandScheduler.getInstance().run() 放在 robotPeriodic()，所以 Test 模式下排程器照樣運作；testInit() 的 cancelAll() 則確保進入 Test 時先把其他指令停掉。
