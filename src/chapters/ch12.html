CAN ID 12｜硬體

感測器與 CAN 除錯：計步器、刻度尺和廣播線

機器人要知道自己在哪，靠的是感測器；感測器要能讀到，靠的是 CAN。這章講 TalonFX 內建編碼器和 CANcoder 差在哪、CANcoder 零點怎麼設、極限開關怎麼接、怎麼歸零。最後是我覺得最實用的部分：CAN 上找不到裝置的時候，照什麼順序查。

版本說明這章是照 WPILib 2026 和 Phoenix 6 的 2026 版（26.x）文件寫的。CANcoder 的 AbsoluteSensorRange 從 2025 年起改名叫 AbsoluteSensorDiscontinuityPoint，網路上舊範例還會看到舊名字。

先講個比喻：班長的計步器、牆上的刻度尺

班長身上戴著一個計步器，走一步就加一，很靈敏、反應很快。但它只知道「從早上戴上到現在走了幾步」，每天早上都從 0 開始算。昨天放學班長停在走廊中間，今天早上計步器一樣從 0 開始，它根本不知道自己在哪。

走廊牆上則有一把刻度尺，什麼時候看都能直接讀出「現在在第幾公尺」，一大早看也是對的。只是刻度尺裝上去的時候，0 不一定剛好對準走廊起點，所以要記一個「校正值」，讀到的數字加上校正值才是真的位置。

走廊盡頭還有一個門擋。門擋只會告訴你「碰到了」或「還沒」，講不出距離多遠，但拿來確認「已經到底了」剛剛好。而且一碰到門擋，就知道現在一定在盡頭，可以順便把計步器對準。

學校的廣播線是一條串起來的線，從廣播室出發，一間教室接一間教室，最後接到走廊盡頭。線的兩端各要裝一個吸音墊，不然聲音跑到底會反彈回來，跟新的廣播疊在一起，聽起來全是回音。中間哪一段被剪斷，斷點後面的教室就通通聽不到。

所以某班點名沒人回應的時候，要照順序找：先確定是不是兩個班長用了同一個代號，再沿著廣播線一段一段查，看是從哪一間開始聽不到的。

這個比喻哪裡不準刻度尺是直的，CANcoder 量的卻是旋轉，轉滿一圈就回到同一個讀數。所以 CANcoder 只能在「一圈以內」告訴你絕對角度。如果它跟機構之間還有減速，機構轉不到一圈它可能已經轉好幾圈了，這時它也不知道自己在第幾圈。要把 CANcoder 裝在「機構整個行程不超過一圈」的軸上，絕對位置才有意義。

三種感測器，各自適合做什麼

感測器告訴你什麼開機時適合
TalonFX 內建編碼器馬達轉了幾圈、轉多快從 0 開始滾輪、飛輪速度；搭配歸零的升降機構

WPILib 的建議也差不多：極限開關只感測得到一個位置，拿來確保不超過極限很好，但不適合在快到極限時控制速度；手臂的旋轉關節最好用絕對編碼器這類感測器來控制，極限開關當後備，萬一編碼器壞了還能防止機構跑過頭[1]。

CANcoder：設定零點與方向

CANcoder 是一顆接在 CAN 上的磁性旋轉編碼器[2]。CTRE 範例的設定是這樣寫的[3]：

CANcoder armEncoder = new CANcoder(23, CANBuses.CANIVORE); // TODO: 依接線

CANcoderConfiguration ccConfig = new CANcoderConfiguration();
// 讀數範圍的「斷點」：0.5 代表讀數在 -0.5 到 0.5 圈之間
ccConfig.MagnetSensor.withAbsoluteSensorDiscontinuityPoint(Rotations.of(0.5));
ccConfig.MagnetSensor.SensorDirection = SensorDirectionValue.CounterClockwise_Positive; // TODO: 上機確認
ccConfig.MagnetSensor.withMagnetOffset(Rotations.of(0.0)); // [MEASURED] TODO: 依下面的步驟量測
armEncoder.getConfigurator().apply(ccConfig);

三個設定分別是：

  • SensorDirection：哪個方向轉算正。要跟 TalonFX 的 Inverted 一致，也就是手臂往上的時候，兩邊讀數都要變大。
  • AbsoluteSensorDiscontinuityPoint：讀數在哪裡從最大跳回最小。設 0.5 的話讀數就在 -0.5 到 0.5 圈之間。這個斷點要放在手臂永遠到不了的角度，不然手臂經過那裡讀數會突然跳一圈。
  • MagnetOffset：校正值。量法：先把 offset 設 0、套用設定，把手臂擺到你定義的 0 度（例如水平），讀出 CANcoder 的絕對位置 x，offset 就填 −x。
教練提醒：offset 要寫進程式只要重裝磁鐵、拆裝 CANcoder，零點就會變。offset 寫在 Constants 裡、註明哪天量的，比只存在 Tuner X 裡可靠得多。第 11 章講過：程式套用的完整設定會蓋掉你在 Tuner X 手動改的值。

讓 TalonFX 直接讀 CANcoder

第 6 章的手臂用的是 TalonFX 內建編碼器，SensorToMechanismRatio 填馬達到手臂的齒輪比。加了 CANcoder 之後，可以讓 TalonFX 直接拿 CANcoder 當回授來源，閉迴路還是在控制器裡跑[4]：

TalonFXConfiguration config = new TalonFXConfiguration();
config.Feedback.FeedbackRemoteSensorID = armEncoder.getDeviceID();
config.Feedback.FeedbackSensorSource = FeedbackSensorSourceValue.RemoteCANcoder;
config.Feedback.SensorToMechanismRatio = 1.0; // TODO: CANcoder 轉數 / 手臂轉數
config.Feedback.RotorToSensorRatio = 1.0;     // TODO: 馬達轉數 / CANcoder 轉數
// ...其他設定同第 6 章
armLeader.getConfigurator().apply(config);

注意，這時候「sensor」換人了：用遠端 CANcoder 時，SensorToMechanismRatio 是 CANcoder 到手臂的比例。CANcoder 直接裝在手臂轉軸上就是 1.0，不是馬達的齒輪比。這個超容易填錯。

FeedbackSensorSource做什麼需要 Pro
RemoteCANcoderCANcoder 在 CAN 上發布資料時，TalonFX 就更新位置與速度不需要
FusedCANcoder把 CANcoder 和馬達內建編碼器融合，兼顧準確與反應速度需要
SyncCANcoder開機時用 CANcoder 對齊內建編碼器，之後用內建編碼器控制，並持續監看兩者是否差太多需要

沒有 Pro 授權的話，FusedCANcoder 和 SyncCANcoder 會退回 RemoteCANcoder，還會觸發 UsingFusedCANcoderWhileUnlicensed 故障[4]。RotorToSensorRatio 是馬達轉數對 CANcoder 轉數的比例；CTRE 在講手臂重力補償時也特別要求，用絕對感測器就要把這個比例設好，而且位置 0 要代表手臂水平向前[5]。

極限開關

接在 roboRIO 的 DIO

roboRIO 內建的數位輸入有內部上拉電阻，所以預設會讀到 high[6]。換句話說，DigitalInput.get() 在什麼都沒接的時候回傳 true。開關接到地線的話，接通讀 false、斷開讀 true。

所以你一定要先想清楚：「線掉了」會被讀成什麼？

開關種類沒碰到碰到線掉了
常開（NO），接地truefalsetrue（看起來像沒碰到）
常閉（NC），接地falsetruetrue（看起來像碰到）

用常開開關，線掉了程式會以為「還沒到底」，繼續往下推；用常閉開關，線掉了程式會以為「已經到底」，機構就停住了。後者比較安全，因為壞掉的時候是停，不是撞。這是我們選接法的理由，不是唯一答案，但不管怎麼接，這張表一定要寫在程式註解裡。

/** 常閉開關接 DIO 0：碰到或線掉了都回傳 true。 */
private final DigitalInput bottomLimit = new DigitalInput(0); // TODO: 依接線

public boolean atBottom() {
    return bottomLimit.get();
}

想讓 TalonFX 碰到開關就停止往那個方向輸出，可以把開關狀態直接塞進控制請求[7]：

motor.setControl(request.withOutput(volts)
    .withLimitReverseMotion(atBottom()));

接在 TalonFX 上

開關也可以直接接到 TalonFX 的極限開關接腳，由控制器自己停止輸出，完全不經過 roboRIO。讀狀態用 getForwardLimit() / getReverseLimit()，值是 ClosedToGround 就代表開關接通[7]。Phoenix 6 還可以設定碰到開關時自動把位置設成某個值（*LimitAutosetPositionValue）[8]，等於控制器自己幫你歸零。

歸零（homing）

只有內建編碼器的升降機構，開機的時候不知道自己在哪。常見做法是開機後先慢慢往下，碰到底部開關就把位置設成 0。第 6 章的 ArmIO 已經留好 resetPosition 了，這章的練習會把它串成一個指令。

開關會抖機械開關在接觸的那一瞬間會快速通斷好幾次。如果「碰到」會觸發一次性的動作，像重設位置，可以用 WPILib 的 Debouncer：輸入要持續改變一段時間，輸出才會跟著變[9]。

CAN 的接法

CAN 建議用 daisy-chain 接法：從 roboRIO 出發，一個裝置進、一個裝置出，最後接到 PDP。黃線是 CAN-High、綠線是 CAN-Low[10]。CAN 網路兩端都要有一顆 120 Ω 的終端電阻，roboRIO 和 PDP 都內建了，所以才建議從 roboRIO 開始、PDP 結束[10]。CANivore 也內建終端電阻，用 CANivore 的話就是「CANivore ↔ 裝置 ↔ 120 Ω 電阻」[11]。

檢查接線有一招很好用：斷電之後拿電錶量 CAN-H 和 CAN-L 之間的電阻，應該大約 60 Ω（兩顆 120 Ω 並聯）。量到 120 Ω 就是只有一端有終端[11]。

找不到裝置時的除錯順序

CAN 的問題說穿了通常只有兩種：同型號的裝置用了一樣的 ID（出廠預設都是 0），或是 CAN 線接錯、接不牢。最麻煩的是兩種同時發生[11]。照 CTRE 建議的順序查：

  1. 看 Tuner X。同型號、同 ID 的裝置會變成紅色卡片，標示衝突[11]。注意是「同型號」：TalonFX 21 和 CANcoder 21 不會衝突，兩顆 TalonFX 21 才會。
  2. 看哪些裝置不見了。daisy-chain 某一段斷掉，斷點後面的裝置會全部消失。找出「最後一個還在的」和「第一個不見的」，問題就在這兩個中間。
  3. 一條一條拉拉看。有接頭的地方，每一根壓接的線都輕輕拉一下；壓接不良是「時好時壞」最常見的原因[11]。
  4. 看顏色。每個接點都要黃接黃、綠接綠，黃綠接反是新機器人最常見的錯之一[11]。
  5. 斷電量電阻。大約 60 Ω 才對。
  6. 還是找不到，就縮小範圍。只接一個裝置，確認它出現、設好 ID、貼標籤，再一個一個接回去，接到問題出現為止[11]。

看燈號也有幫助：TalonFX 和 Pigeon 2 正常但沒被控制時通常閃橘燈，CANcoder 是快速亮閃；LED 偶爾閃一下紅，通常是接點鬆了，可以搖一搖線看能不能重現[11]。

動手試：CAN bus 除錯台

下面是一條接在 CANivore「9427」上的 CAN bus。點裝置之間的線可以剪斷或接回，也可以拔掉末端的終端電阻、故意把 ID 設錯。每弄壞一個地方，就按「斷電量電阻」和「Tuner X 掃描」看會怎樣。多玩幾次，比賽時你會感謝自己。

在程式裡發現斷線

第 6 章的 ArmIOHardware 已經用 refreshAll(...).isOK() 把 leaderConnected 填進點名表了。可是光記錄沒用，要讓操作手在比賽中看得到才行。WPILib 的 Alert 類別可以發持續性的警告，儀表板會照嚴重程度和時間排好；建議的用法是在 periodic 裡呼叫 set，讓它自己偵測變化決定什麼時候亮[12]。

public class ArmSubsystem extends SubsystemBase {
    private final Alert leaderDisconnected =
        new Alert("手臂主馬達（ID 21）斷線", AlertType.kError);
    private final Debouncer leaderDebounce = new Debouncer(0.5, Debouncer.DebounceType.kFalling);

    @Override
    public void periodic() {
        io.updateInputs(inputs);
        // 連續 0.5 秒讀不到才算斷線，避免偶爾掉一個封包就跳警告
        leaderDisconnected.set(!leaderDebounce.calculate(inputs.leaderConnected));
        // ...其餘同第 6 章
    }
}

kFalling 只延遲「true 變 false」的那個方向：恢復連線時警告馬上清掉，斷線要持續 0.5 秒才跳出來[9]。0.5 秒只是示範，可以看需求調。

常見錯誤

以為內建編碼器知道位置沒歸零的升降機構，開機讀到 0 不代表它在底部。關機時如果停在半空中，開機後「回到 0」的指令會讓它直接往下撞。
CANcoder 的斷點放在行程中間手臂經過斷點時讀數跳一整圈，閉迴路以為誤差突然暴增，手臂就猛甩一下。斷點要放在手臂到不了的角度。
SensorDirection 和 Inverted 不一致馬達往上推，CANcoder 卻說在往下，閉迴路越修越錯，手臂直接衝到底。上機先用低電壓手動轉，確認兩邊讀數往同一個方向增加。
用常開開關，卻沒想過線會掉比賽中線被撞掉，程式以為還沒到底，機構就一直往下推。先想清楚「線掉了會讀成什麼」。
量電阻沒斷電通電時量到的數字不準，還可能把電錶弄壞。一定要斷電再量。

小測驗

練習：升降機構的歸零指令

假設升降機構只有 TalonFX 內建編碼器，底部有一個常閉極限開關接在 DIO 0。在 ElevatorSubsystem 寫一個 home() 指令：用很小的電壓往下，碰到開關就停，然後把位置重設成 0。為了避免開關壞掉時一直往下推，加一個 3 秒逾時。

先想清楚：常閉開關什麼時候讀到 true？如果是逾時結束的，可以把位置當成 0 嗎？

可以用 startEnd（開始給小電壓、結束停止）加 .until(this::atBottom) 與 .withTimeout(3.0)，最後 andThen(runOnce(...)) 重設位置。

重設位置前再檢查一次 if (atBottom) io.resetPosition(0.0);，逾時結束就不重設；開關讀值可以先過 Debouncer。

public class ElevatorSubsystem extends SubsystemBase {
    private static final double HOMING_VOLTS = -1.0; // TODO: 實測，越小越安全
    private static final double HOMING_TIMEOUT_S = 3.0; // TODO: 依行程調整

    /** 常閉開關：碰到或線掉了都回傳 true。 */
    private final DigitalInput bottomLimit = new DigitalInput(0); // TODO: 依接線
    private final Debouncer bottomDebounce = new Debouncer(0.05, Debouncer.DebounceType.kRising);
    private boolean atBottom = false;

    private final ElevatorIO io;
    // ...inputs、其他欄位與第 6 章手臂相同

    @Override
    public void periodic() {
        atBottom = bottomDebounce.calculate(bottomLimit.get()); // 每輪只讀一次
        // ...
    }

    public boolean atBottom() {
        return atBottom;
    }

    public Command home() {
        return startEnd(
                () -> io.setVoltage(HOMING_VOLTS),
                () -> io.stop())
            .until(this::atBottom)
            .withTimeout(HOMING_TIMEOUT_S)
            .andThen(runOnce(() -> {
                if (atBottom) {
                    io.resetPosition(0.0);
                }
            }))
            .withName("Elevator.home");
    }
}

講幾個重點。until 和 withTimeout 誰先發生都會結束（第 10 章）；結束後再確認一次 atBottom，如果是逾時結束的，就不要重設位置，不然會把錯的位置當成 0。另外用常閉開關的話，線掉了會讀成「已經到底」，機構會停在原地被當成 0，所以開機歸零之後，還是要用眼睛確認機構真的在底部。

這個寫法為了短，直接在 startEnd 裡呼叫 IO。如果你的 Subsystem 跟第 6 章一樣在 periodic 裡送輸出，就要改成切換 ControlMode，不然會被 periodic 蓋掉。
