CAN ID 16｜上場

自動階段與路徑：校外教學的行程表

讀完這章，你會知道場地座標怎麼定、里程計怎麼估計機器人位置以及它為什麼會飄、PathPlanner 的路徑和 Auto 怎麼變成指令，以及紅藍聯盟翻轉、Named Commands、自動程式選單這些上場前一定要處理好的細節。

版本說明本章依據 WPILib 2026 與 PathPlannerLib 2026 的文件。PathPlanner 的 API 每年都可能改，網路上舊的範例（例如 2024 年以前的 HolonomicPathFollowerConfig）已經不能用。本章以 swerve 底盤為例。

生活比喻：校外教學的行程表

老師不能跟車，全靠行程表。校外教學的前 15 分鐘，老師必須留在學校，遊覽車只能照事先寫好的行程表走。路線怎麼開、在哪一站下車做什麼，都要提前寫好。

司機靠里程表和方向盤估計位置。車上沒有 GPS，司機只能記「往北開了多少公里、在哪裡左轉」，推算現在在哪裡。短程很準，但開久了、中途被別的車擦撞一下，推算就會越來越偏。

地圖的原點永遠在藍色校門。學校有紅、藍兩個校門，兩邊的路線剛好左右對稱。地圖只畫一份，原點永遠在藍色校門；從紅色校門出發時，就把整份路線翻過去用。

每一站要做的事，用代號寫在行程表上。行程表上寫「到博物館：活動 A」。活動 A 是什麼，出發前老師要先跟領隊說清楚；如果出發後才說，領隊手上的行程表早就印好了，不會知道活動 A 要做什麼。

好幾份行程表，出發前選一份。老師準備了幾份行程表：天氣好走 A 路線，下雨走 B 路線。出發前在黑板上選好，遊覽車就照那一份走。

這個比喻哪裡不準遊覽車偏了司機會看路標修正；機器人的里程計自己不會修正，要靠第 17 章的視覺定位（AprilTag）才能把位置拉回來。另外，路線「翻過去」的方式取決於當年的場地：WPILib 文件說明，FRC 的場地有「鏡射」和「旋轉」兩種配置，不同年份不一樣[1]。上場前一定要在紅方實際跑一次，確認翻轉後的路徑是對的。

場地與機器人的座標

WPILib 大多數情況使用 NWU 慣例：X 軸正向朝前、Y 軸正向朝左、Z 軸朝上；角度 0° 對齊 +X，逆時針為正，所以 90° 是 +Y[1]。兩個要特別注意的地方[1]：

  • 有些陀螺儀是順時針為正，讀值要確認方向，必要時反過來。
  • 搖桿用的是另一套座標（NED）：往前推是負的 Y、往右推是正的 X。把搖桿值交給底盤時，常常需要加負號。

里程計：機器人怎麼知道自己在哪

里程計用輪子的編碼器和陀螺儀，推算機器人在場上的位置（Pose2d：x、y、朝向）。WPILib 文件說明：因為只用編碼器和陀螺儀，估計的位置會隨時間漂移，特別是和其他機器人碰撞時；不過在自動階段通常非常準確[2]。所以自動階段靠里程計跑路徑是可行的，但每次開始前都要把位置設對。

用 CTRE Tuner X 產生的 swerve 程式，底盤會自己維護里程計，getState().Pose 就是目前估計的位置[3]。

PathPlanner 是什麼

PathPlanner 分成兩部分：電腦上的 GUI，用來畫路徑、組 Auto；機器人程式裡的 PathPlannerLib，負責讀檔並跟隨路徑。PathPlannerLib 可以用 WPILib 的 Vendor Dependency Manager 安裝[4]（第 0 章的 vendordep）。

在 GUI 裡，Path 是一條路線；Auto 是一個 sequential 指令群組，裡面可以放路徑跟隨指令、Named Commands、等待指令和巢狀的指令群組，同一條路徑可以在多個 Auto 裡重複使用[5]。換句話說，Auto 就是第 10 章的組合指令，只是用 GUI 畫出來。

Robot Config

GUI 的設定頁要填機器人的質量、轉動慣量（MOI）、輪子與馬達等資料，PathPlanner 用它們限制軌跡的最大速度、加速度。文件提醒這些值要盡量準確：質量要含保險桿和電池；MOI 建議用 SysId 的結果計算，粗估的公式假設質量均勻分布，通常不準[6]。這裡又用到第 15 章的 SysId。

設定 AutoBuilder

PathPlannerLib 用 AutoBuilder 把 GUI 裡的 Auto 變成指令，文件建議在底盤 Subsystem 的建構子裡設定[7]。以下是 CTRE 官方 swerve + PathPlanner 範例的寫法[3]：

private void configureAutoBuilder() {
    try {
        var config = RobotConfig.fromGUISettings();
        AutoBuilder.configure(
            () -> getState().Pose,   // 目前位置
            this::resetPose,         // Auto 有起始位置時，用它重設里程計
            () -> getState().Speeds, // 目前速度（機器人座標）
            (speeds, feedforwards) -> setControl(
                m_pathApplyRobotSpeeds.withSpeeds(ChassisSpeeds.discretize(speeds, 0.020))
                    .withWheelForceFeedforwardsX(feedforwards.robotRelativeForcesXNewtons())
                    .withWheelForceFeedforwardsY(feedforwards.robotRelativeForcesYNewtons())),
            new PPHolonomicDriveController(
                new PIDConstants(10, 0, 0),  // 平移 PID（範例值，要實測）
                new PIDConstants(7, 0, 0)),  // 旋轉 PID（範例值，要實測）
            config,
            () -> DriverStation.getAlliance().orElse(Alliance.Blue) == Alliance.Red, // 紅方時翻轉
            this);
    } catch (Exception ex) {
        DriverStation.reportError("Failed to load PathPlanner config and configure AutoBuilder", ex.getStackTrace());
    }
}

逐項看：

  • 速度必須是機器人座標（robot relative），不是場地座標[7]。
  • PID：路徑跟隨本身有前饋，PID 只修正「實際位置和路徑的差距」，這和第 13 章的觀念一樣。
  • 翻轉：最後一個參數回傳 true 時，路徑會翻到紅方那一側。文件特別強調原點永遠在藍方；如果需要其他依聯盟顏色的轉換，要自己處理[7]。
  • 最後的 this：讓路徑跟隨指令 require 底盤 Subsystem（第 8 章）。
DriverStation.getAlliance() 可能是空的它回傳 Optional：還沒連上 Driver Station 或 FMS 時沒有值。上面的寫法用 orElse(Alliance.Blue) 預設藍方。這也是為什麼「是否翻轉」要寫成 lambda，在路徑開始跑的時候才判斷，而不是開機時就決定。

Named Commands

Auto 和路徑上的事件標記（event marker）要執行機構動作時，用的是名字。程式裡要用 NamedCommands.registerCommand 把名字和指令對起來，名字必須和 GUI 裡完全一樣[8]。

public RobotContainer() {
    // 1. 建立 Subsystem
    // 2. 註冊 Named Commands（一定要在建立任何 Auto 或 Path 之前）
    NamedCommands.registerCommand("armScore", arm.goTo(ArmState.SCORE));
    NamedCommands.registerCommand("armStow", arm.goTo(ArmState.STOW));
    NamedCommands.registerCommand("intake", intake.intakeUntilHasPiece());
    // 3. 建立自動程式選單
    autoChooser = AutoBuilder.buildAutoChooser();
    SmartDashboard.putData("Auto Chooser", autoChooser);
    // 4. 按鍵綁定
    configureBindings();
}
順序很重要文件警告：Named Commands 必須在建立任何 PathPlanner Auto 或 Path 之前註冊；之後才註冊的，已經建立的 Auto 不會用到它。建議在 RobotContainer 裡、Subsystem 建立之後、其他指令建立之前註冊[8]。

事件標記還有一個容易忽略的規則：路徑跑到終點時，所有由事件標記觸發的指令都會被要求結束。如果想在路徑結束時才啟動某個動作，應該放在 Auto 裡、或放在下一條路徑的開頭[5]。

intake.intakeUntilHasPiece() 是示範名稱，代表「吸到遊戲物件才結束」的指令。Auto 是 sequential 群組，所以放進去的指令一定要會結束，否則後面的步驟永遠不會開始（第 10 章）。第 6 章的 goTo 用 until(this::atGoal) 結束，剛好適合。

自動程式選單與載入時機

AutoBuilder.buildAutoChooser() 會建立一個包含專案中所有 Auto 的 SendableChooser，預設選項是 Commands.none()，也可以傳入名字指定預設的 Auto[7]。然後第 7 章的 getAutonomousCommand() 只要回傳選到的那一個：

public Command getAutonomousCommand() {
    return autoChooser.getSelected();
}
  • 開機時就載入。文件強烈建議在程式啟動時就建立所有 Auto，而不是要跑的時候才建立，因為載入複雜的路徑可能造成很大的延遲[7]。buildAutoChooser 在建構子裡呼叫，本身就符合這個建議。
  • 刪掉的 Auto 還在選單裡？它會載入 deploy 資料夾裡的所有 Auto；build.gradle 要有 deleteOldFiles = true，否則刪掉的檔案不會從 roboRIO 上清掉[7]。

上場前的自動程式檢查

  1. 選單裡選的是這一場要跑的 Auto，而且不是預設的「None」。
  2. 機器人擺放的位置和 Auto 的起始位置一致（Auto 有設起始位置時，會用 resetPose 重設里程計）。
  3. Driver Station 上的聯盟顏色正確，路徑會往正確的一側翻。
  4. 在練習場或模擬（第 6 章 D 部分）裡，紅藍兩邊都實際跑過一次。

常見錯誤

Named Command 名字不一致GUI 裡叫 ArmScore、程式裡註冊 armScore，大小寫不同就對不上，Auto 跑到那一步什麼都不做。
在 Auto 裡放不會結束的指令例如 run(...) 做成的預設指令，整個 Auto 就卡在那一步。
陀螺儀方向相反順時針為正的陀螺儀沒反過來，里程計的朝向就和實際相反，路徑跟隨一轉彎就走錯方向，場地導向駕駛也會亂掉。
開機時判斷聯盟顏色在 RobotContainer 建構子裡讀 getAlliance()，那時可能還沒連上 FMS，拿到的是空值或錯的顏色。
Robot Config 亂填質量、MOI、輪徑填錯，PathPlanner 產生的軌跡會超過機器人做得到的加速度，路徑越跑越偏。

小測驗

練習：兩段式自動程式

不用 GUI，只用程式組出一個 Auto：先把手臂移到 SCORE、等手臂到位後跑一條叫 "Leave" 的路徑，同時把手臂收回 STOW。提示：AutoBuilder.followPath(PathPlannerPath.fromPathFile("Leave")) 會回傳跟隨這條路徑的指令，而 fromPathFile 可能丟出例外。

看參考答案 
private Command buildLeaveAuto() {
    try {
        PathPlannerPath leave = PathPlannerPath.fromPathFile("Leave");
        return Commands.sequence(
            arm.goTo(ArmState.SCORE),
            Commands.parallel(
                AutoBuilder.followPath(leave),
                arm.goTo(ArmState.STOW)))
            .withName("LeaveAuto");
    } catch (Exception e) {
        DriverStation.reportError("Failed to load path Leave: " + e.getMessage(), e.getStackTrace());
        return Commands.none();
    }
}

// RobotContainer 建構子裡，buildAutoChooser 之後
autoChooser.addOption("Leave（程式）", buildLeaveAuto());

幾個重點：sequence 等手臂到位才出發；parallel 讓走路徑和收手臂同時進行，兩者都結束才算完成（第 10 章），手臂和底盤是不同的 Subsystem，不會互相打斷。載入失敗時回傳 Commands.none() 並回報錯誤，比讓整支程式當掉好。這個 Auto 在建構子裡就建好，符合「開機時載入」的建議。

注意這條路徑沒有經過 PathPlannerAuto，所以不會自動重設起始位置；實際使用時要確認里程計在出發前已經設對。
