Lambda 與方法參考：給代課老師的字條

讀完這章，你會看懂 () -> 和 ::，分得清「交出一個做法」和「當場執行一個方法」，並避開搖桿數值只讀一次的經典 bug。

生活比喻：導師出差前留的字條

字條本身不是動作。導師明天要出差，放學前在講桌上留了一疊字條給代課老師。導師寫字條的時候，什麼事都沒發生，沒有人被叫去做任何事。字條裡裝的是「做法」，要等代課老師在適當的時機拿起來照做。

字條有四種。第一種是單純交代一件事：「第一節下課時，請值日生擦黑板。」代課老師照做，不需要回報什麼。第二種是請他查一個數字：「看一下教室溫度是幾度。」查完會得到一個數字。第三種是請他判斷是或否：「看一下外面有沒有下雨。」答案只有有或沒有。第四種是對某個人做一件事：「把這份考卷發給＿＿＿。」代課老師要在空格填上一個人，然後照做。

有些字條只寫「照某某的做法」。點名的流程班長每天都在做，導師不必重寫一遍，字條上只寫：「點名，照班長平常的做法。」

「看溫度」和「寫溫度」差很多。有一張字條寫：「現在 18 度，冷的話幫大家關窗。」另一張寫：「看一下現在幾度，冷的話幫大家關窗。」導師寫字條時是早上 7 點、18 度，代課老師下午 2 點拿起字條時已經 30 度了。照第一張做，他會在大熱天把窗戶關上；照第二張做，他會自己去看溫度，判斷才會對。

字條上的名字寫了就不能改。導師寫「把考卷交給班長小明」，之後就算班長換人，代課老師也不知道該交給誰。所以學校規定：字條上引用的名字，寫上去之後導師就不能再改動那個名字代表的人，不然字條的意思會變得不清楚。

Command-based 程式到處都是這種字條。你告訴 WPILib「按下 A 鍵時做這件事」，WPILib 會在按鍵被按下的那一刻才去執行。WPILib 文件把這個觀念稱為「把函式當成資料」[1]。

這些「字條格式」在 Java 裡叫函式介面（functional interface）：只有一個抽象方法的介面[2]。它們大多在 java.util.function 套件裡，Runnable 則在 java.lang[3]。

這個比喻哪裡不準字條是一張紙，但 Java 的 lambda 在執行時其實是一個物件，這個物件實作了對應的函式介面（例如 Runnable）。這也是為什麼它能被存進變數、當成參數傳來傳去，和第 1 章學的物件沒有兩樣。

Lambda 的寫法

Lambda 的格式是「參數 → 要做的事」[4]。空括號 () 表示不收參數；只有一個參數時可以省略括號；要做的事超過一行，就用大括號包起來。

// IntakeSubsystem 裡：回傳一個指令，執行時給一次電壓就結束
public Command ejectOnce() {
    return runOnce(() -> setRollerVoltage(-6.0));
}

// 執行中每個週期給電壓，結束時停止：兩張「交代一件事」的字條
public Command runRoller(double volts) {
    return runEnd(() -> setRollerVoltage(volts), () -> setRollerVoltage(0.0));
}

runOnce 收一個 Runnable；runEnd 收兩個，一個是執行中每次要做的事，一個是結束時要做的事。字條都交給 WPILib，由它決定什麼時候執行[1]。這些指令 API 的細節在第 8、9 章。

方法參考：「照某某的做法」

// 結束時要做的事，已經有 stopRoller() 寫好了，直接指過去
public Command runRollerUntilReleased(double volts) {
    return runEnd(() -> setRollerVoltage(volts), this::stopRoller);
}

// 把「讀左搖桿 Y 軸」這個方法交出去，而不是讀出一個數字
DoubleSupplier leftY = controller::getLeftY;

方法參考的格式是 物件::方法 或 類別::靜態方法[5]。WPILib 文件特別提醒：:: 後面不加括號，因為這裡是把方法本身交出去，而不是呼叫它[1]。

最重要的一件事：寫溫度 vs 看溫度

下面是 FRC 最常見的錯誤之一（drive 是一個假設的底盤 Subsystem）：

// 錯：寫溫度。只在綁定的那一刻讀一次搖桿
double speed = -controller.getLeftY();
drive.setDefaultCommand(drive.run(() -> drive.arcadeDrive(speed, 0.0)));

controller.getLeftY() 有括號，所以它在這一行就被執行了，得到一個固定的數字。之後 lambda 每次執行，用的都是那個數字，搖桿怎麼推機器人都不會變。

// 對：看溫度。每次執行都重新讀搖桿
drive.setDefaultCommand(
    drive.run(() -> drive.arcadeDrive(-controller.getLeftY(), -controller.getRightX())));

讀搖桿的程式碼寫在 lambda 裡面，所以每次指令執行（每 20 毫秒）都會重新讀一次。加負號是因為搖桿往前推時 Y 軸讀到的是負值。

字條上的名字不能改Lambda 只能使用 final 或「實際上沒被改過」（effectively final）的區域變數[4]。上面錯誤範例裡的 speed 就是 effectively final，所以編譯器不會報錯，這正是這個 bug 難抓的原因：程式完全合法，只是邏輯錯了。

BooleanSupplier 與 Trigger

// 按住 A 鍵時吸入
controller.a().whileTrue(intake.runRoller(8.0));

// 自訂條件：右扳機按超過一半時吐出
new Trigger(() -> controller.getRightTriggerAxis() > 0.5)
    .whileTrue(intake.runRoller(-6.0));

Trigger 的建構子收一個 BooleanSupplier，也就是「看一下有沒有下雨」這種字條。排程器每個週期都會拿起來看一次。

教練提醒看到「搖桿推了機器人沒反應」或「數值永遠是 0」，先檢查搖桿讀取有沒有寫在 lambda 外面。這個 bug 我每一屆新生都會遇到。

小測驗

練習：找出 bug，再寫一個條件

第一題：下面這段程式想讓機器人在按住 B 鍵時，用右搖桿 X 軸控制轉向，但轉向完全沒反應。指出原因並修正。

double turn = -controller.getRightX();
controller.b().whileTrue(drive.run(() -> drive.arcadeDrive(0.0, turn)));

第二題：寫一個 BooleanSupplier，在左、右扳機都按超過一半時回傳 true。

看參考答案

第一題：getRightX() 在綁定按鍵時就被呼叫了，turn 是固定值。要把讀取搬進 lambda：

controller.b().whileTrue(drive.run(() -> drive.arcadeDrive(0.0, -controller.getRightX())));

第二題：

BooleanSupplier bothTriggers = () ->
    controller.getLeftTriggerAxis() > 0.5 && controller.getRightTriggerAxis() > 0.5;
