Lambda 與方法參考：給代課老師的字條

Command-based 的程式裡到處都是 () -> 和 ::，第一次看會覺得很像亂碼。這章把它們拆開講，重點是分清楚「把做法交出去」跟「當場執行」的差別。搞懂這個，你就不會踩到那個每屆都有人踩的搖桿 bug。

先講個比喻：導師出差前留的字條

導師明天要出差，放學前在講桌上留了一疊字條給代課老師。重點是：導師在寫字條的當下，什麼事都沒發生，沒有人被叫去做事。字條裡裝的是「做法」，要等代課老師在對的時間拿起來照做。

字條大概有四種。第一種單純交代一件事：「第一節下課請值日生擦黑板。」照做就好，不用回報。第二種是查一個數字：「看一下教室幾度。」查完會拿到一個數字。第三種是判斷是或否：「看一下外面有沒有下雨。」答案只有有或沒有。第四種是對某個人做事：「把這份考卷發給＿＿＿。」代課老師要在空格填一個人再照做。

有些事班長每天都在做，像點名，導師就不用再寫一次流程，字條上只寫「點名，照班長平常的做法」。

接下來是最重要的一個例子。有一張字條寫：「現在 18 度，冷的話幫大家關窗。」另一張寫：「看一下現在幾度，冷的話幫大家關窗。」導師寫字條是早上 7 點、18 度，代課老師下午 2 點拿起來的時候已經 30 度了。照第一張做，他會在大熱天把窗戶關起來；照第二張，他會自己去看溫度，這樣判斷才對。

最後一個規矩：導師寫了「把考卷交給班長小明」，之後如果班長換人，代課老師就不知道該交給誰了。所以學校規定，字條上寫到的名字，寫上去之後就不能再改它代表誰，不然字條的意思會亂掉。

Command-based 程式裡到處都是這種字條。你跟 WPILib 說「按 A 鍵的時候做這件事」，它會等到真的有人按 A 那一刻才去做。WPILib 文件管這個叫「把函式當成資料」[1]。

比喻Java收什麼 → 回傳什麼在 WPILib 裡
交代一件事Runnable無 → 無指令要執行的動作
查一個數字DoubleSupplier無 → 數字持續讀取搖桿數值
判斷是或否BooleanSupplier無 → 是／否Trigger 的條件
對某人做一件事Consumer<T>一個東西 → 無指令結束時收到「是否被中斷」
當場寫一張字條Lambda () -> ...當場定義一個做法
「照班長的做法」方法參考 ::指向一個已經寫好的方法
寫溫度 vs 看溫度呼叫 vs 傳遞加括號就是當場執行
字條上的名字不能改effectively finalLambda 只能用不再被改動的區域變數

這幾種「字條格式」在 Java 裡叫函式介面（functional interface），意思是只有一個抽象方法的介面[2]。大部分放在 java.util.function 套件，Runnable 比較特別，在 java.lang[3]。

這個比喻哪裡不準字條只是一張紙，但 Java 的 lambda 執行時其實是一個物件，實作了對應的函式介面（例如 Runnable）。所以它才能被存進變數、當參數傳來傳去，跟第 1 章學的物件沒什麼兩樣。

Lambda 的寫法

Lambda 就是「參數 → 要做的事」[4]。空括號 () 代表不收參數；只有一個參數的話括號可以省略；要做的事超過一行，就用大括號包起來。

// IntakeSubsystem 裡：回傳一個指令，執行時給一次電壓就結束
public Command ejectOnce() {
    return runOnce(() -> setRollerVoltage(-6.0));
}

// 執行中每個週期給電壓，結束時停止：兩張「交代一件事」的字條
public Command runRoller(double volts) {
    return runEnd(() -> setRollerVoltage(volts), () -> setRollerVoltage(0.0));
}

runOnce 收一個 Runnable。runEnd 收兩個，一個是執行中每次要做的事，一個是結束時要做的事。字條交給 WPILib 之後，什麼時候執行就是它的事了[1]。這些指令 API 第 8、9 章會細講，現在看得懂字條在哪就好。

方法參考：「照某某的做法」

// 結束時要做的事，已經有 stopRoller() 寫好了，直接指過去
public Command runRollerUntilReleased(double volts) {
    return runEnd(() -> setRollerVoltage(volts), this::stopRoller);
}

// 把「讀左搖桿 Y 軸」這個方法交出去，而不是讀出一個數字
DoubleSupplier leftY = controller::getLeftY;

方法參考的寫法是 物件::方法 或 類別::靜態方法[5]。注意 :: 後面不加括號，因為你是把方法本身交出去，不是呼叫它[1]。

最重要的一件事：寫溫度 vs 看溫度

這是 FRC 最常見的錯誤之一，真的很常見（drive 是假設的底盤 Subsystem）：

// 錯：寫溫度。只在綁定的那一刻讀一次搖桿
double speed = -controller.getLeftY();
drive.setDefaultCommand(drive.run(() -> drive.arcadeDrive(speed, 0.0)));

controller.getLeftY() 有括號，所以在這一行就執行了，拿到一個固定的數字。之後 lambda 每次跑，用的都是那個數字，你搖桿怎麼推機器人都不理你。

// 對：看溫度。每次執行都重新讀搖桿
drive.setDefaultCommand(
    drive.run(() -> drive.arcadeDrive(-controller.getLeftY(), -controller.getRightX())));

讀搖桿那段寫在 lambda 裡面，所以指令每次執行（每 20 毫秒）都會重讀一次。前面加負號，是因為搖桿往前推的時候 Y 軸讀到的是負的。

字條上的名字不能改Lambda 裡只能用 final 或「實際上沒被改過」（effectively final）的區域變數[4]。上面錯誤範例的 speed 剛好就是 effectively final，所以編譯器一聲不吭。這也是這個 bug 難抓的原因：程式完全合法，只是邏輯錯了。

BooleanSupplier 與 Trigger

// 按住 A 鍵時吸入
controller.a().whileTrue(intake.runRoller(8.0));

// 自訂條件：右扳機按超過一半時吐出
new Trigger(() -> controller.getRightTriggerAxis() > 0.5)
    .whileTrue(intake.runRoller(-6.0));

Trigger 的建構子收一個 BooleanSupplier，就是「看一下有沒有下雨」那種字條，排程器每個週期都會拿起來看一次。

教練提醒只要聽到「搖桿推了機器人沒反應」或「數值永遠是 0」，先去看讀搖桿的那行是不是寫在 lambda 外面。這個 bug 每一屆新生都會遇到，真的每一屆。

小測驗

練習：找出 bug，再寫一個條件

第一題：下面這段想讓機器人在按住 B 鍵時用右搖桿 X 軸轉向，結果轉向完全沒反應。為什麼？怎麼改？

double turn = -controller.getRightX();
controller.b().whileTrue(drive.run(() -> drive.arcadeDrive(0.0, turn)));

第二題：寫一個 BooleanSupplier，左右兩個扳機都按超過一半的時候回傳 true。

第一題：想想 turn 是什麼時候算出來的？算完之後還會變嗎？

把讀搖桿的呼叫搬進 lambda 裡，每次執行才會重讀。BooleanSupplier 就是「沒有參數、回傳 boolean」的 lambda。

第一題改成 drive.arcadeDrive(0.0, -controller.getRightX())；第二題是 () -> controller.getLeftTriggerAxis() > 0.5 && controller.getRightTriggerAxis() > 0.5。

第一題：getRightX() 在綁按鍵的時候就被呼叫了，turn 從此就是固定值。要把讀取搬進 lambda：

controller.b().whileTrue(drive.run(() -> drive.arcadeDrive(0.0, -controller.getRightX())));

第二題：

BooleanSupplier bothTriggers = () ->
    controller.getLeftTriggerAxis() > 0.5 && controller.getRightTriggerAxis() > 0.5;
