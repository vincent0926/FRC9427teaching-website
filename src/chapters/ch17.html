CAN ID 17｜上場

視覺與定位：看門牌校正位置

讀完這章，你會知道 AprilTag 是什麼、為什麼要把視覺量測「融合」進里程計而不是直接取代、標準差代表什麼、怎麼用 Limelight 的 MegaTag2 更新 CTRE swerve 的位置，以及兩種瞄準做法的差別。

版本說明本章依據 WPILib 2026 文件，以及 CTRE Phoenix6-Examples 附的 LimelightHelpers。Limelight 與 PhotonVision 的韌體與函式庫每年更新，使用前請對照當年的版本。本章延續第 16 章，以 CTRE swerve 為例。

生活比喻：看門牌校正位置

靠步數記位置，走久了會偏。第 16 章的校外教學，司機靠里程表推算位置。走得越久、被擦撞越多次，推算就偏得越多。

路邊有門牌。每棟建築物門口都釘著一塊門牌，門牌的位置在地圖上早就標好了。看到門牌、量出自己離它多遠、在它哪一側，就能算出自己在地圖上的哪裡。

但看門牌也會看錯。門牌很遠的時候看不清楚，估出來的距離誤差很大；同時看到兩三塊門牌，就準得多。車子在急轉彎時看出去的畫面是糊的，這時候看到的最好別信。

所以不是「看到門牌就全聽它的」。聰明的司機會把兩種資訊合起來：步數推算很穩但會慢慢偏，門牌很準但偶爾會跳。門牌看得清楚時多信門牌一點，看不清楚時多信自己的推算。

方向盤比門牌更知道車頭朝哪。車頭朝哪個方向，看車上的指南針就很準，不需要靠遠方的門牌推算。

比喻程式
靠步數記位置里程計（編碼器 + 陀螺儀）
地圖上標好位置的門牌場上位置已知的 AprilTag
看門牌算出自己在哪視覺位置估計（vision pose）
遠的門牌看不清楚距離越遠，量測的標準差越大
急轉彎時畫面糊掉高速旋轉時的量測不可靠，應丟掉
兩種資訊合起來、看情況決定信誰位置估計器（pose estimator）的融合
車上的指南針陀螺儀的朝向
這個比喻哪裡不準司機看到門牌是「現在」看到的；相機的影像從拍攝、處理到送進程式，中間有延遲。位置估計器會用量測的時間戳，把這筆資料對回「拍照那一刻」機器人在哪裡，所以時間戳一定要正確。

AprilTag

WPILib 文件說明：AprilTag 是密西根大學研究人員開發的視覺標籤系統，能以低運算量提供高精度的定位；在 FRC 裡，它讓機器人知道自己在場上的位置，以便對準目標。從 2023 年起，場上散布著多個 AprilTag，每一個都在已知的位置；從 2024 年起使用 36h11 家族[1]。

練習場自己貼 AprilTag 時要注意：文件提醒要把標籤固定在硬的背板上保持平整，因為辨識演算法假設標籤是平的[1]。

融合，而不是取代

WPILib 提供 SwerveDrivePoseEstimator 等位置估計器，可以直接取代里程計，並把「有延遲補償的視覺位置」和編碼器、陀螺儀的量測融合在一起[2]。用法是每一輪呼叫 update 放入里程計資料，偶爾有視覺結果時呼叫 addVisionMeasurement[2]。CTRE 的 swerve 底盤已經內建同樣的機制，所以直接呼叫 drivetrain 的 addVisionMeasurement 就好[3]。

標準差：你有多相信這筆資料

WPILib 文件說明，位置估計器可以設定模型和量測的標準差。標準差描述雜訊有多分散；給某個量越小的標準差，融合時就越相信它。例如把視覺量測的標準差調大，估計器就比較不受雜亂的視覺資料影響，代價是修正偏差比較慢[2]。

針對 AprilTag，文件給了三條具體建議[2]：

  • 視覺的朝向標準差設得非常大（朝向交給陀螺儀）。
  • 陀螺儀的朝向標準差設得小。
  • 視覺的 x、y 標準差隨著和標籤的距離放大。

動手試：信誰多一點

下面把問題簡化成一維：里程計說機器人在 x = 3.00 m，視覺說在 x = 3.40 m。調整兩者的標準差，看融合後的估計會落在哪裡。這是用「變異數倒數加權」算的，和位置估計器（卡爾曼濾波）融合時的想法一樣。

這個實驗裡，視覺的標準差設成「0.05 m × 距離²，看到多個標籤時除以標籤數」。這只是示範用的經驗式，不是官方公式；隊上要用實際資料調整。

用 Limelight 更新位置

CTRE 的 swerve 範例附了一段 Limelight 整合的程式，使用 LimelightHelpers 的 MegaTag2 位置估計[4]。MegaTag2 需要先告訴 Limelight 機器人的朝向，LimelightHelpers 的註解寫明呼叫 getBotPoseEstimate_wpiBlue_MegaTag2 之前要先呼叫 SetRobotOrientation，而且 yaw 為 0 代表機器人面向紅方牆面，也就是第 16 章「原點在藍方」的場地座標[5]。

下面照 CTRE 範例的流程，加上文件建議的「距離越遠越不信」：

private static final String LL = "limelight"; // TODO: 和 Limelight 網頁設定的名稱一致

@Override
public void robotPeriodic() {
    CommandScheduler.getInstance().run();

    var drivetrain = m_robotContainer.drivetrain; // CTRE 範例把底盤放在 RobotContainer
    var state = drivetrain.getState();
    double headingDeg = state.Pose.getRotation().getDegrees();
    double omegaRps = Units.radiansToRotations(state.Speeds.omegaRadiansPerSecond);

    // 1. 先告訴 Limelight 機器人朝哪
    LimelightHelpers.SetRobotOrientation(LL, headingDeg, 0, 0, 0, 0, 0);
    // 2. 取得 MegaTag2 的位置估計
    var est = LimelightHelpers.getBotPoseEstimate_wpiBlue_MegaTag2(LL);
    // 3. 沒看到標籤、或正在快速旋轉時丟掉
    if (est != null && est.tagCount > 0 && Math.abs(omegaRps) < 2.0) {
        double xyStd = 0.05 * est.avgTagDist * est.avgTagDist / est.tagCount; // TODO: 依實測調整
        drivetrain.addVisionMeasurement(
            est.pose,
            est.timestampSeconds,
            VecBuilder.fill(xyStd, xyStd, 9999999)); // 朝向幾乎不信視覺，交給陀螺儀
    }
}

幾個重點：

  • 旋轉太快就丟掉。CTRE 範例的門檻是每秒 2 圈[4]。範例的註解也說明，這段程式只是示範「可以整合視覺」，通常還需要依距離和標籤數調整標準差，實際做法要依隊伍需求調整[4]。
  • 時間戳的時基。CTRE swerve 的 addVisionMeasurement 在範例裡被覆寫，用 Utils.fpgaToCurrentTime 把 FPGA 時間轉成 Phoenix 的時基再交給底盤[3]。用 Tuner X 產生的 CommandSwerveDrivetrain 已經包含這段；自己寫的話不能漏掉。
  • 朝向交給陀螺儀。第三個標準差設極大，對應 WPILib 的建議[2]。
放在 IO 架構裡本章為了對照 CTRE 範例，把程式寫在 robotPeriodic。依第 6 章的架構，比較好的做法是寫一個 VisionIO（硬體版讀 Limelight、模擬版回傳空結果；重播時和第 6 章一樣用空實作，資料由日誌填回），讓 Vision Subsystem 在 periodic 裡取得結果再交給底盤，這樣視覺資料也能被記錄與重播（第 18 章）。

PhotonVision 是另一套常見的開源選擇，也能在協同處理器上辨識 AprilTag 並輸出位置估計，最後同樣交給 addVisionMeasurement。不管用哪一套，「融合、依距離調整標準差、丟掉不可靠的量測」這三件事都一樣。

瞄準的兩種做法

做法怎麼算優點缺點
直接用畫面偏移相機回報目標在畫面中心左右幾度（Limelight 的 tx），用 PID 轉到 0簡單，不需要場地座標看不到目標就不能用；相機不在旋轉中心時會有誤差
用估計的位置從估計的 Pose2d 和目標在場上的座標，算出該朝哪個角度看不到目標也能轉；和自動階段用同一套座標位置估計要準，視覺融合要做好

LimelightHelpers.getTX 回傳準心到目標的水平偏移角度（度），getTV 回傳是否有看到目標[5]。第一種做法大致如下：

private final PIDController aimPid = new PIDController(0.0, 0.0, 0.0); // TODO: 輸入度，輸出 rad/s

public Command aimWithTx(DoubleSupplier forward, DoubleSupplier strafe) {
    return drivetrain.applyRequest(() -> {
        double rot = LimelightHelpers.getTV(LL)
            ? aimPid.calculate(LimelightHelpers.getTX(LL), 0.0)
            : 0.0; // 沒看到目標就不轉
        return driveRequest
            .withVelocityX(forward.getAsDouble())
            .withVelocityY(strafe.getAsDouble())
            .withRotationalRate(rot);
    });
}

PID 的輸出正負號一定要上機確認：WPILib 的旋轉是逆時針為正（第 16 章），而 tx 的正負代表目標在準心的哪一側，兩者方向不一定相同。先把 kP 設很小，確認機器人是「轉向」目標而不是「轉離」目標，再慢慢加大。

第二種做法用第 16 章的座標：目標在場上的座標減掉機器人的座標，得到一個向量，它的角度就是機器人應該面對的方向，再交給 CTRE 的 FieldCentricFacingAngle 之類「朝向固定角度」的請求。這種做法在紅方時要記得目標座標也要換成紅方那一個。

常見錯誤

看到標籤就直接 resetPose視覺量測偶爾會跳，直接把位置重設成它，機器人在場上會瞬間移位，路徑跟隨跟著亂跑。用 addVisionMeasurement 融合。
時間戳用錯時基把 FPGA 時間直接交給 CTRE swerve 而沒有轉換，估計器會把量測對到錯的時間點，位置被拉來拉去。
相機位置沒量準Limelight 要知道相機裝在機器人上的哪裡、朝哪個角度。這組數字錯了，所有視覺位置都會偏。
忘了呼叫 SetRobotOrientationMegaTag2 需要機器人的朝向，沒有提供時結果不可靠。
練習場的標籤貼歪、沒貼平演算法假設標籤是平的，彎曲或位置跟場地圖不一致的標籤會讓練習時的結果和正式比賽不同。

小測驗

練習：記錄被丟掉的量測

在上面的視覺程式裡，加上兩個計數：接受了幾筆量測、因為旋轉太快丟掉幾筆，每輪用 SmartDashboard.putNumber 顯示。想一想：這兩個數字在比賽中能幫你發現什麼問題？

看參考答案 
private int acceptedCount = 0;
private int rejectedSpinCount = 0;

// robotPeriodic 裡
if (est != null && est.tagCount > 0) {
    if (Math.abs(omegaRps) < 2.0) {
        acceptedCount++;
        drivetrain.addVisionMeasurement(est.pose, est.timestampSeconds,
            VecBuilder.fill(xyStd, xyStd, 9999999));
    } else {
        rejectedSpinCount++;
    }
}
SmartDashboard.putNumber("Vision/Accepted", acceptedCount);
SmartDashboard.putNumber("Vision/RejectedSpin", rejectedSpinCount);

如果整場比賽 Accepted 幾乎沒增加，可能是相機沒連上、名稱打錯、曝光設定不對，或是機器人大部分時間都看不到標籤。如果 RejectedSpin 很多，代表門檻可能太嚴，或是駕駛習慣一直邊轉邊移動。把這些數字記錄下來（第 18 章），賽後就能回頭查。
